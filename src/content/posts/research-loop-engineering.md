The defining skill shift of the past year is easy to miss because it sounds like jargon: practitioners are moving from prompt engineering to *loop engineering* — designing the system that prompts the model, rather than typing each prompt yourself. The term has been popularized in the developer community, but the underlying pattern comes straight from frontier-lab engineering practice.

Anthropic's foundational essay [Building effective agents](https://www.anthropic.com/research/building-effective-agents) defined an agent as a model "using tools in a loop": at each iteration the system assembles context, the model reasons and selects an action, the action executes, and the observed result feeds the next iteration. The essay's much-quoted advice — find the simplest loop that works, and add complexity only when it demonstrably improves outcomes — remains the discipline's first principle. Workflows with predefined steps are cheaper and more predictable; full agent loops earn their cost only on open-ended problems.

What changed in 2025–2026 is how much engineering now goes into each leg of that loop. Anthropic's [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) reframes the input side: context is a finite resource with diminishing marginal returns, so the loop must curate "the smallest possible set of high-signal tokens" each turn — via compaction, structured note-taking, just-in-time retrieval, and sub-agents with isolated contexts — rather than stuffing everything into one window. The action side received the same treatment in [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents), which argues tools should be designed and evaluated against the agent's loop, not a human API consumer: consolidated operations, token-efficient responses, and unambiguous naming measurably change what the loop converges to.

The newest frontier is loops that outlive any single context window. Anthropic's [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) describes the mechanics: because the model forgets everything between sessions, state must live outside the loop — a feature list, a progress file, git history — so each fresh iteration can orient itself, do one increment of verifiable work, and write its state back down. Anthropic's [C compiler experiment](https://www.anthropic.com/engineering/building-c-compiler) pushed this further, running parallel Claude instances against a shared goal for weeks; the loop design, including how work was partitioned and verified, mattered as much as the model. OpenAI codified the same primitives — sessions, handoffs, guardrails, and tracing around the run loop — into its [Agents SDK](https://openai.com/index/new-tools-for-building-agents/), so developers configure loops rather than hand-roll them.

The practical lesson: the questions that matter have moved up a level. Not "what should I say to the model?" but "what does the loop read when it wakes up, how does it verify an iteration succeeded, and where does it write what it learned?" Verification deserves special weight — Anthropic's harness writing keeps returning to tests, typed feature lists, and committed progress notes because a loop without a ground-truth check compounds errors as efficiently as it compounds progress. Teams that answer those three questions well get compounding progress from the same models everyone else is using; teams that don't get impressive demos that stall after the first context window.
